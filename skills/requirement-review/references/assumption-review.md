# 关键假设核验

## 对象与边界

审查需求定义中支撑问题成立、用户范围、场景、实用性或用户价值的关键主张：如果该主张不成立，上述判断会实质改变。候选包括问题频率、受影响角色、当前替代方式的局限、原因解释、使用前提和增量价值。只保留与当前需求直接相关的关键项，合并重复项，不要求固定数量。

本方法服务于现有需求评审，不扩展为产品策略评估、方案设计、实验设计、需求优先级或上线放行。输入出现具体方案时，仅检查其是否被偷换为问题或用户价值成立的前提；方案效果标为待验证，不据此扩展审查范围。

## 核验方法

1. 引用原始主张及来源，保留角色、场景、范围与限定条件。先说明现有证据为何可能支持它，再寻找实际反证或证据缺口；不攻击被弱化的主张，不凭空制造缺陷。
2. 区分已有证据支持的结论、待验证假设和无法判断的事项。缺少证据不等于主张已被证伪；已有可靠证据支持时明确写出支持依据和剩余限制。
3. 写出可观察、可核验的失效条件，说明它将改变哪项需求判断。使用“若观察到……，则……判断不成立或需缩小范围”的表达，避免“用户不喜欢”“执行风险”等泛化描述。
4. 指明能区分支持与反对的最小必要证据，包括证据类型、适用角色与场景、需核验的字段或现象，以及已有来源或建议证据责任角色。可建议查阅现有日志、工单、访谈记录或规则；不编造数据、样本、来源、责任人姓名或数值阈值。来源尚未取得时明确标为待获取。
5. 只有缺口会改变问题定义、范围、实用性或用户价值是否成立时，才形成 BLOCKING Finding；其他限制为 NON_BLOCKING。不得因为它被称为“关键假设”、暂时缺证据或存在失败可能，就自动阻塞。证据不足以判断影响时说明未知及阻塞判定依据。

## 输出与后续

按需加入以下表格；篇幅较短时使用等价的逐项说明：

| ID / 原始主张及来源 | 关键假设与现有支持/反证 | 失效条件及影响 | 所需证据及待获取来源 | 结论 / 关联 Finding |
|---|---|---|---|---|

结论使用“已有支持 / 待验证 / 已有反证 / 无法判断”，并说明证据限制。核验本身不产生独立 PASS 或否决结论；最终仍使用现有 PASS、CORRECTED、NEED_HUMAN_CONFIRMATION。

证据责任角色未知时标为待指定。优先复用当前有效且可追溯的资料，不强制新增访谈或实验。若确需新研究、测试或业务阈值，输出待确认的证据问题并交由责任人决定，不擅自制定实验、停止标准或业务取舍。提供反证后按现有 Finding 和人工确认规则处理，Reviewer 不自行重写问题定义。

## 示例：批量审批需求

原始主张：“审批慢主要因为需要逐条操作。”

- 关键假设：逐条操作是目标角色在目标审批场景中的主要耗时来源；引用需求中的实际依据，无依据时标为假设。
- 失效条件：若可追溯的环节耗时记录表明，等待审批人或资料补全才是主要耗时来源，则“逐条操作是主要原因”的解释不成立；审批慢这一问题仍可能成立，不能一并否定。
- 所需证据：覆盖目标角色与场景的现有审批环节时间戳、操作耗时记录，以及必要的工单或访谈记录；数据缺失时列明待获取内容，不虚构比例或阈值。
- 处理：按原因判断是否影响当前问题定义与范围决定阻塞性，不直接推荐批量审批或其他替代方案。
