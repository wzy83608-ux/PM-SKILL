# 验收设计：按业务语义选取，不机械穷举

## 覆盖矩阵

先枚举真实导航、二级页、弹窗、角色专属页，再将模块映射到以下适用动作。计划中的每个动作有一个用例 ID，执行后更新为通过/失败/阻塞/未测；多个动作合成一条记录时写清子步骤，不隐藏未执行部分。

| 功能形态 | 实际操作与核对点 |
|---|---|
| 列表与查询 | 默认数据、搜索命中/无结果/清空、筛选组合、排序、分页、筛选后操作是否命中正确对象 |
| 详情 | 与列表一致、关联对象可达、字段单位和状态可理解、空值不误导 |
| 新增与编辑 | 必填、重复、合法/非法格式、边界值、取消不落库、保存后重开、修改历史、生效时点 |
| 关联配置 | 上下级依赖、停用对象、关联变更影响、团队/个人/多对象名单及排重；全局配置只读核对或使用隔离副本 |
| 草稿与提交 | 草稿保存范围、重开恢复、遗漏校验、重复点击、提交快照、已提交可否修改 |
| 审批 | 发起人、实际接收人、节点顺序、同层多人语义、指定人/代理人、通过/退回/重提/撤回（适用时）、最终生效 |
| 角色与数据范围 | 可见入口、可操作按钮、被禁止操作的提示；正向与反向核验。避免只用管理员测全流程 |
| 导入 | 模板实际下载、字段/单位、合法与非法混合行、重复策略、预览计数、提交后成功/跳过/失败数和持久化一致 |
| 导出 | 任务创建、进度终态、下载文件、实际打开文件核对表头/行数/筛选范围。按钮成功不等于文件正确 |
| 计算与分配 | 独立预期公式、基数、币种、汇率时点、阶梯/累计/最高档、上限、顺序、余额、0与空值、舍入差额 |
| 通知与本人结果 | 下一角色实际收到任务，结果用户可查、对象和期间正确、最终状态一致 |
| 结束/冻结/归档 | 确认弹窗、结果持久化、只读、历史与当前口径分离，适用时核对恢复路径 |

删除、状态切换、全局规则变更、真实通知发送按用户授权及宿主规则执行；不能测的明确标记，不为追求动作数量越权。

## 主流程用例

以一组有辨识度的测试数据贯穿：基础配置 → 创建业务对象 → 关联参与者 → 下发任务/目标 → 拆分 → 审批 → 执行/数据回填 → 评价 → 计算/分配 → 确认 → 各角色查看结果。系统没有的环节不添加。

每次角色交接，记录“谁、通过哪个页面、把哪个对象、交给谁、对象从何状态变成何状态、审批单号”。候选审批人不是实际操作人，同层任一通过也不等于所有候选人均审批。

主流程先跑一组可闭环数据，再补关键反向/边界。阻塞要验证明确错误或稳定缺失，而不是页面仍在加载。独立模块继续推进，依赖该节点的下游记为阻塞。

## 名单完整性专项

建立期望集合及角色关系：业务负责人、团队负责人、团队成员、直接参与者；如适用还包括外部协作者。对每个人记录其目标承接层级和下游状态。

逐层对账：

1. 配置中的团队/个人与其实际成员。
2. 第一层分配界面全部承接对象；故意漏填一对象测试提交是否阻断（在安全的草稿内）。
3. 团队拆分界面的全部应分配成员；负责人是否由团队目标代表，以明确规则为准。
4. 审批快照与生效后的详情；目标页签计数的含义不能混淆。
5. 考评对象与最终分配名单；重复参与是否汇总、按路径分列或阻止，需按规则核对。
6. 各账号本人页面。只有管理者列表有名字不等于本人已收到可见目标。

计数必须解释，例如“1名业务负责人＋团队6人＋直接个人1人＝8名唯一人员”。重复成员按 ID 去重，有角色重叠时报告对象条数和唯一人数两种计数，不仅比姓名。

## 计算专项

从页面配置建立可手算预期，再与程序结果比较。记录金额、单位、舍入精度与规则版本；发现差异先检查基数、规则版本、时点、封顶/余额，不能为使测试通过而手工改成预期值。手工调整流程可另测，但原自动结果及差异必须保留。

对总分、比例、费用、奖励等守恒关系，只检查系统明确要求的约束。公司预算可超配、个体目标可独立百分比等均不能套用未经确认的“必然应相加为100%”假设。
