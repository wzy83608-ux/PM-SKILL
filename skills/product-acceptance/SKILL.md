# 产品功能验收

本 Skill 不依赖特定项目、AI 品牌、浏览器插件或业务领域。使用当前 AI 环境可用且获准的 UI/连接器工具执行；本文件也可作为其他 AI 的任务指令入口。没有操作工具时只能输出准备清单和明确的未执行项，不能把推演写成实测。

## 交付目标

让用户知道：实际测了什么、哪个角色如何流转、输入及结果是否一致、哪里阻断、证据在哪里、还有什么没测。默认输出轻量 HTML 报告、原始测试记录及截图目录，报告采用白底卡片、蓝色标题、橙色结论栏、覆盖表、问题详单和两列截图画廊。不要把本项目的角色、地址、月份、金额或账号固化为通用要求。

## 开始与连续执行

1. 读取用户本轮范围、已授权操作、历史已确认的业务口径、忽略事项以及适用工具规则。建立运行目录和持续写入的测试记录，长任务中及时保存，恢复时先读记录再续做。
2. 从用户指定系统及可见导航发现模块、角色、状态和依赖；读取已有报告或需求中的验收标准。缺少标准时，区分页面明确承诺、业务不变量、推测三种依据。只问确实阻塞执行的信息。
3. 记录环境、测试时间和时区、页面可见版本、账号角色（不记密码）、数据范围、模拟数据标识及风险操作边界。发现数据集或版本变化时切分测试阶段；不能把不同阶段的现象混为同一版本结论。
4. 参考 [验收设计](references/test-design.md) 制定模块×操作×角色覆盖表，以及跨角色主流程。按风险分配深度，不能把“打开页面”当作“模块全部通过”。
5. 执行已授权的测试数据创建、保存、提交和跨角色操作，直到流程闭环或遇到具体阻塞。遵守当前宿主安全规则；本 Skill 不额外授予权限，不要求为普通可逆测试反复确认。生产环境的删除、权限扩大、真实支付等不能因“全量验收”而自动获得授权。

## 实测方法

- UI 验收以真实可见页面为主。连接器/API 可补充已授权核对，但必须标记来源；API 成功不能代替页面交互通过，不得用后台写入掩盖 UI 卡点。
- 每次动作后观察实际状态，等待明确完成/失败信号。失败先检查当前页面，避免盲点重复提交。结果不明时先查有无已创建记录，再决定重试，防止重复数据。
- 对保存/草稿：关闭重开或刷新核对持久化；对提交：核对审批快照、当前节点、接收角色和生效状态；对结束：核对只读状态及下游结果。列表、详情和本人视角出现差异时追踪到底。
- 逐人核对参与名单、目标/任务分配名单、审批快照、考评名单、最终结果名单。团队、直接个人、负责人可能位于不同层级或页签，必须先合并语义再判断是否遗漏。负责人承接团队目标、固定奖励不单独评分等需以该系统规则为准。
- 金额、数量和比例要用独立算式核对基数、币种、单位、阶梯算法、顺序、封顶、余额及舍入；区分目标未分配、已分配但奖励为零、规则不适用和配置缺失。不要把零值自动判成 Bug。
- 选取有意义的缺填、无效值、边界、取消、退回/重提、权限和导入异常测试；仅在适用且获准时执行。不要为了“细致”修改全局审批或权限，影响既有业务。
- 使用唯一测试前缀及合理模拟数据，记录每个新建对象的 ID、关联及最终状态；原有记录仅在授权范围内改动。清理与否明确记录，不默认永久删除。
- 持续提供简洁进度：已验证事实、发现的问题、下一步，不用预设“全部通过”。单点阻塞时记录并继续独立模块；无法继续的依赖项列为阻塞，不能假装完成。

## 证据与判断

按 [证据与报告约定](references/evidence-report.md) 记录每条用例、截图和问题。报告数据格式见 [记录契约](references/run-contract.md)。

- 异常应包含输入前后、触发动作、实际提示、关闭重开/其他角色的结果；截图应可辨认账号角色、对象、周期/状态。不能用事后空表截图证明之前输入丢失。
- 先保存原始截图；凭真实字节识别 PNG/JPEG，不依赖后缀猜测。隐藏或裁去密码、令牌等无关敏感信息；标注图不可替代原图。截图未截到关键区域时应补拍，不得引用空白图。
- 分开记录：已复现缺陷、体验建议、规则待确认、暂时忽略、已修复、未复现、阻塞、未测试。用户确认正常或要求忽略后，更新当前结论和计数，保留历史证据及依据；不声称根因已被证明。
- 疑似异步加载、环境异常先做适度等待和有限复核；一次暂态不能直接定为持久故障。保留当时与复核结果，禁止无依据推断前后端、数据库或代码原因。
- 严重级别按实际影响判断：P0 数据/安全灾难；P1 核心闭环阻断或严重数据错误；P2 局部功能不可用/结果错误；P3 文案、可理解性或轻微体验。业务口径未确定时先列待确认，不强行定缺陷。

## 报告生成与交付

1. 持续维护 `run.json`，确保每项结论关联用例和证据；详细动作、审批链和逐人核对不得只在聊天里。
2. Node.js 可用时执行 `node <skill>/scripts/render-report.mjs <run.json> <output-dir>`；它生成 `report.html` 并将引用截图复制为相对路径。默认轻量版，分享时携带整个输出目录或打包 ZIP。无需 Node 时按同样结构手工生成静态 HTML，不必安装依赖。
3. 报告必须包含：结论与范围限制、测试环境/阶段、实际业务链路、逐角色/逐对象结果、模块覆盖、可复现问题、测试数据及未覆盖范围、截图全集。无依据的栏目留空说明或删去，不能补造。
   - HTML 报告默认提供左侧章节菜单：桌面端固定显示，点击跳转对应章节并标注当前章节；小屏可改为顶部或折叠菜单，不能遮挡正文。
   - 验收记录必须支持“全部／通过／未通过”结果筛选；阻塞、未测试等其他判定单独展示，不能混为未通过。支持关键词组合搜索、匹配数量、无结果提示和重置筛选。筛选只改变显示，不修改原始记录及报告总计。
4. 验证报告中用例/人数/截图计数、所有图片路径、页面编码、导航锚点；实际打开渲染并检查首屏、表格和至少一张关键截图。验证结果筛选、组合搜索、空结果、重置，以及左侧菜单跳转；切换筛选不能丢失证据链接。打不开就查文件、展示模式、图片路径及工具限制，不直接归咎用户。HTML 要正常分行，避免一行数 MB 的内嵌图片导致预览只显示行号。
5. 用可用的宿主工具在用户要求的位置打开报告。工具返回 queued 不等于已可见；无法视觉核验须如实说明。最终提供可点击文件链接、关键结论和一张能证明核心结果的截图，不输出账号密码汇总。

## 调用示例

“使用 product-acceptance，对这个系统按现有角色做完整验收，允许创建测试数据；重点核对团队和直接参与者是否全部收到目标，异常截图，报告沿用 Skill 的图文格式。”

“使用 product-acceptance 复测上一份报告的 P1/P2 项，用户已确认的正常规则不再计为缺陷；仅报告实际复测结果，未能复现的保留原证据并更新状态。”
