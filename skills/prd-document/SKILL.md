# PRD 需求文档生成与审查

## 通用原则

本 Skill 不依赖固定目录、专用脚本、本地记录库、特定版本编号或其他 Skill。输入可以是产品设计、会议决定、原型、需求分析、用户资料、Huly 证据、历史产品文档或可核验的公开资料。缺失正式版本链时仍可生成 `STANDALONE_DRAFT`。

PRD 中的事实、规则、结论、指标、流程和范围必须有明确依据。允许的依据类型为：用户或业务事实、互联网来源、过往产品资料、经确认的业务知识、可核验的行业知识。AI 常识、合理猜测和未经确认的经验不能作为确定内容写入 PRD，只能进入待确认项或被省略。

面向读者的需求文档正文不得出现 `[E01]`、`[E02]` 等证据编号或类似的内部溯源标记。证据关系仅用于生成与审查过程，可集中记录在附录的自然语言来源清单、评审记录或内部结构化账本中；正文保持业务可读性。除非用户明确要求显示逐条引用，否则不得把内部证据 ID 插入标题、段落、表格、验收标准或待确认事项。

## 简洁表达与表格优先

- 不要产生大段文字。每段只说明一个主题；多个条件、操作、结果或异常应拆为短句、分点或步骤。表格内外均适用，使用简洁、易懂的语言。
- 能用表格清楚表达的内容优先使用表格，包括需求范围、页面与字段清单、角色权限、状态、业务规则、流程步骤、异常处理及对比关系。短引言或不适合表格的内容保留简短说明，不为表格而增加复杂度。
- 表格按主题拆分，每行表达一个场景或一组相关规则；单元格仍用短句和必要的分点，不能把大段文字搬进表格。
- 精简与表格化只调整表达，不丢失逻辑和需求；完整保留条件关系、先后顺序、阈值、时间窗口、权限及例外。

## 表格单元格的结构化排版

- 撰写或整理需求表格时，每个单元格中的长段文字必须按语义拆为短段、项目列表或编号步骤，不把多个条件、操作、结果和异常处理堆成一段。
- 同一单元格包含多类规则时，使用简短小标题分组，例如“适用对象”“触发条件”“系统处理”“用户反馈”“异常与恢复”；只使用与该格内容有关的分组，不套用空标题。
- 并列规则使用项目列表，有先后顺序的流程使用编号步骤；条件分支分条表达，保留“且／或”、阈值、时间窗口、权限边界和例外条件，避免因拆分改变业务含义。优先使用目标编辑器支持的原生列表和段落，不叠加项目符号与编号。
- 已有表格的格式调整须保留完整原文含义、单元格归属及行列对应关系，不借排版增删或改写已确认的业务规则。短句无需强行拆分。
- 调整列宽与换行，使长内容正常显示，避免文字挤压、异常空白和不必要的横向溢出。保存后核对内容与表格结构；可读取实际页面时检查最终显示，不能仅凭写入成功认定排版完成。

## 表格外正文的结构化排版

- 结构化排版同样适用于表格外的正文，包括字段说明、业务规则、权限说明、异常处理、配置与原型边界、需求问答；不得仅整理单元格而保留其他大段堆叠文字。
- 根据语义使用小标题、短段和原生列表：并列说明用项目列表，实际操作顺序用编号步骤，多类内容按主题分组。不要仅按标点机械切分，也不要把无先后关系的说明全部编号。
- 需求问答的提问与简短直接回答分别成段；回答含多项规则时在其后分点展开，避免把“答：是”等短答单独列成编号步骤。
- 调整只改变呈现结构，须保留规则含义、条件关系、阈值、权限、例外及来源；消息模板、代码和需要逐字保留的文本维持其原有格式。保存后核对内容完整性和实际阅读效果。

## 正式文档只呈现需求说明

正式需求文档只保留当前有效的需求、业务规则、流程、权限、异常处理，不保留聊天问答、协商过程、确认往返、修改经过或已放弃方案。将已确认结论直接写入对应需求章节；重复结论合并到现有规则，不能简单把“需求问答”改名后继续堆放。用户明确要求的独立评审记录、变更记录或待确认事项可另行保留，与正式需求说明区分。

## 不输出验收标准

需求文档不编写或保留“验收标准”“验收条件”“AC”及同类验收清单，也不将其换名后放入其他章节。正文只描述需求范围、功能、交互、业务规则、状态、权限及异常处理；需求应清晰，但无需附带验收条目。本要求优先于本 Skill 参考文件中建议附带验收标准的通用格式。仅当用户后续明确要求单独撰写验收或测试材料时，才按该次授权另行输出。

## 工作流程

1. 阅读 [证据与引用规则](references/prd-evidence-policy.md)，建立证据账本并判断每项输入可支持什么内容。
2. 阅读 [PRD 就绪检查方法](references/prd-readiness-method.md)，判断现有证据是否足以支持用户要求的内容；真正影响范围、规则、权限或验收的缺口应阻塞。
3. 阅读 [PRD 输出格式](references/prd-structure.md)，按参考文档的章节顺序组织内容。没有适用内容或可靠依据的模块直接省略，不生成空标题、空表格或占位文字。
4. PRD包含产品流程图或交互原型图时，读取 [PRD视觉资产规则](references/prd-visual-assets.md)。流程图必须使用 `$fireworks-tech-graph` 生成，并作为图片直接显示在“产品流程图”正文位置，不能只提供图片路径或附件链接；原型必须给出已验证存在的绝对本地文件地址。
5. 生成正文时读取 [PRD 草稿生成规则](references/prd-draft-generation.md)，为事实性内容建立来源映射。
6. 审查时读取 [PRD Reviewer](references/prd-reviewer.md)，检查格式、证据、完整性、视觉资产和是否存在捏造；区分安全的编辑修正与需要业务 Owner 决定的问题。
7. 需要人工确认或最终审批时，读取对应参考方法；没有记录系统时以带日期、Owner 和版本标识的普通文档记录，不伪造正式 Gate 状态。

## 边界

不重新分析需求，不替用户选择产品方案，不改变已确认范围，不把模板中的编辑提示当成PRD正文，不编写技术架构或开发任务，不声明开发已经获准，也不自动写回任何外部系统。公开资料需要检索时只做与当前PRD相关的最小必要查询，并在正文或附录给出可访问来源、标题和检索日期。
